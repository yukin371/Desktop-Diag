## 1. 阻塞级问题（A 类：不确认无法进入设计）

### A1. 交付时间与 MVP 范围的现实冲突【最高优先级】

- PRD 5 节标题写明「MVP 版本（**国庆可落地 Demo 版**）」，而本次评审日期为 **2026-09-30**，国庆假期当日即开始。
- MVP 声明范围包含 4 大模块：5.1 系统信息结构化采集、5.2 网络连通性智能检测、5.3 系统健康度检测、5.4 三层标准化报告，外加 5.6 两项「可选增强」。
- 评估：5.1–5.4 是**完整可交付产品骨架**（4 个采集域 + 判定引擎 + 报告渲染），工作量真实存在；5.6（启动项 + 磁盘占用分析）单独就接近 5.1–5.3 的量级。
- **风险**：若把 5.6 并入 MVP，极可能挤压测试与工程化阶段，产出「能跑但没测过」的 Demo，反而削弱面试作品可信度。
- **建议**：MVP 冻结为 5.1 + 5.2 + 5.3 + 5.4（不含 5.6）；5.6 顺延至 V1.1，但**在架构上预留采集器注册机制**（阶段 1 落实），使 V1.1 新增采集域无需改动核心。→ 待确认 Q1。

### A2. 「5.6 可选只读增强功能」归属未定义

- 5.6 措辞为「**可选**只读增强功能」「在不修改核心定位的前提下新增」，但未说明它是 (a) MVP 内可选开关、(b) MVP 后 V1.1 内容、还是 (c) 完全可裁剪项。
- 该项技术成本不低：启动项需覆盖 HKLM/HKCU 的 Run/RunOnce、启动文件夹、任务计划（`schtasks` 或 Task Scheduler COM）、系统服务（SCM 枚举），并做**发布者签名校验**（WinVerifyTrust）、路径可疑度判定（临时目录/无签名/异常路径）。
- **建议**：与 A1 合并决策，MVP 不含 5.6。→ 待确认 Q1。

### A3. 报告写入路径未定义 —— 同时是**可用性风险**与**合规表述风险**

- 场景 3.2.2 明确产品最高频用法是「**依托企业内网共享目录直接运行**」。
- 由此产生三个未定义问题：
  1. **可写性**：从 `\\server\share\Desktop-Diag.exe` 直接运行时，进程的「程序所在目录」可能是只读共享，报告写入必然失败；未定义失败时的降级策略。
  2. **合规表述**：写到网络共享目录 = 产生**出站网络写行为**，与 3.3.4「无主动网络数据上传行为」、3.3.5「全程无用户数据上传」的字面表述存在张力（虽属用户主动指定的目标位置，非后台上传，但面试中易被抓）。
  3. **断网场景**：3.2 强调断网可用，若默认写共享目录，断网时写入失败。
- **建议默认策略（待确认 Q2）**：报告写入优先级 = ① 命令行 `-o` 指定目录 → ② EXE 所在目录（若可写） → ③ `%USERPROFILE%\Desktop-Diag\reports\` → ④ `%TEMP%`；并在报告头与结论区**明示实际写入路径与降级原因**。合规表述同步改为「诊断数据仅写入用户指定或本地目录，程序自身无任何后台上传行为」。

### A4. 「无外部依赖」的边界未定义：是否允许编译期第三方库？

- 1.4 表述「无外部依赖」在**运行时**层面成立（Go 静态编译单文件，无运行库、无安装）。
- 但未说明是否允许 `go.mod` 引入第三方模块。这是实质性的架构分岔：
  - **路线甲（允许第三方库）**：`github.com/yusufpapurcu/wmi` + `go-ole` 直取 WMI，开发量最小、字段最全。
  - **路线乙（仅 stdlib + `golang.org/x/sys/windows`）**：完全不碰 WMI/PowerShell/COM，改用 Win32 API（`GetAdaptersAddresses`、`GetSystemTimes`、`GlobalMemoryStatusEx`、`GetDiskFreeSpaceEx`、`GetTickCount64`）+ 只读注册表（`HKLM\SYSTEM\CurrentControlSet\Services\Tcpip\Parameters\Interfaces\{GUID}` 取网关/DNS）。
- **路线乙的关键收益（强烈建议）**：PRD 1.3、5.5、8.2 反复强调「不易被 EDR/组策略拦截」。而 **WMI 查询与 PowerShell 恰恰是 EDR 重点监控的高危行为**。路线乙可实现「零 PowerShell、零 WMI、零 COM、零脚本引擎」，把「不易被拦截」从宣传语变成可验证的架构事实 —— 这是本作品最强的技术差异化点。
- **建议**：采用路线乙为主线（仅 `golang.org/x/sys` 一个半官方依赖），WMI 仅作为降级兜底；若确认允许第三方库，也优先选路线乙，因为依赖更少 = 面试时更难被质疑"不过是包了一层库"。→ 待确认 Q3。

### A5. 权限模型缺失 —— 非管理员终端会出现**静默失败**

- 6.1.4「权限适配检测：区分普通用户/管理员权限可采集项，给出友好权限提示」被排在 **V1.1**。
- 但 MVP 的采集项本身就有权限差异（如系统级启动项、部分事件日志、某些服务信息；网卡/DNS/磁盘/内存基本无需管理员）。
- **风险**：普通用户运行 MVP 时，若某项采集因权限失败，程序若静默跳过，报告会出现「数据缺失但无说明」，运维人员误判为「系统正常」——这与产品「减少漏判」的核心价值**直接冲突**。
- **建议**：MVP 必须包含最小权限自适应能力：① 启动时检测管理员身份；② 单项采集失败时在报告第二层写入「⚠ 该项因权限不足/接口不可用未采集（原因：XXX）」；③ 第一层告警汇总不因采集失败而漏报，改为输出「诊断不完整」提示。→ 待确认 Q4。

## 2. 规则未量化（B 类：无法直接编码为判定逻辑）

判定引擎是本产品与「脚本封装」的分界线（PRD 1.3），但多条告警规则缺少阈值，目前无法写单元测试。

| 编号 | 位置 | 问题 | 建议基线（待确认 Q5） |
| --- | --- | --- | --- |
| B1 | 5.3 | 内存占用率「过高」未定义阈值 | 警告 ≥85%，严重 ≥95% |
| B2 | 5.3 | 采集了 CPU 占用率，但告警规则中**没有 CPU 条目**，是否为遗漏 | 建议补：警告 ≥85%，严重 ≥95%（采样 1s） |
| B3 | 5.2 | 「丢包率、延迟波动」未定义分档 | 丢包 ≥20% 或平均延迟 ≥150ms → 警告；丢包 100% → 严重 |
| B4 | 5.1 | 「DNS 为空/配置异常」只定义了为空 | 补充非法值判定：`0.0.0.0`、`127.0.0.1`、DNS 数量为 0 |
| B5 | 5.3 | 硬编码「C 盘」，未考虑系统盘非 C 的场景（如 C 盘不存在、系统装在 D 盘） | 泛化为「系统盘（`%SystemDrive%`）」 |
| B6 | 5.1 | 只覆盖 IPv4 `169.254/16`，未定义 IPv6 场景 | MVP 判定 IPv6「仅有 `fe80::` 链路本地地址、无全局地址」为同类告警；若确认不做需在 PRD 显式声明「MVP 仅诊断 IPv4」 |
| B7 | 5.4 | 第一层「异常告警汇总」未定义是否分级；6.1.7 分级被排到 V1.1 | MVP 至少需两档（严重/警告）以支撑第一层排序，否则汇总列表无法排优先级 |

## 3. 技术细节歧义（C 类：实现方式不唯一）

| 编号 | 问题 | 建议 |
| --- | --- | --- |
| C1 | 5.2「公共地址 TCP 443 端口连通性探测」未指定具体目标 | 给出候选列表（如 `223.5.5.5:443`、`www.baidu.com:443`），首个成功即判定可达；全部失败才判严重 |
| C2 | 5.2「223.5.5.5 DNS 解析探测」未指定**被解析的域名** | 固定 `www.baidu.com`（国内高可用、解析稳定），并明确走系统 DNS 还是直连 223.5.5.5（建议**两者都做**，可区分「本地 DNS 挂了」与「DNS 服务本身不可达」） |
| C3 | 全部网络探测未定义超时与重试 | ICMP 超时 1s × 4 包；TCP 连接超时 3s；DNS 查询超时 3s |
| C4 | 多网卡场景（有线 + 无线 + VPN 虚拟网卡）未定义网关探测对象 | 过滤出「已启用 + 已连接 + 有默认网关」的物理网卡，**逐网卡分别探测**并分别输出结论 |
| C5 | 报告与控制台的**中文编码**未定义 | 报告写 **UTF-8 with BOM**（保证记事本/Excel 双击不乱码）；控制台启动时切 65001 代码页并设置 UTF-8 输出，避免 GBK 控制台下乱码 |
| C6 | 未定义**进程退出码** | 建议 0 = 无严重告警，1 = 存在严重告警，2 = 程序自身错误（便于接入批处理/巡检流水线） |
| C7 | 未定义任何命令行参数 | MVP 建议仅 `-o <dir>`、`-h`；`-v`（详细）、`--json`（机读输出）列入 V1.1 |
| C8 | 「控制台实时打印检测日志」未定义格式与进度反馈 | 建议 `[n/N] 检测项名 ... 结论` 单行输出，带分级颜色（严重红/警告黄/正常绿，无颜色终端自动降级为纯文本） |
| C9 | 系统运行时长依赖 WMI `LastBootUpTime`，精简系统可能不可用 | 改为 `GetTickCount64()`（Win32 API，必可用），无需 WMI |

## 4. 内部一致性瑕疵（D 类：需修订 PRD 文字）

| 编号 | 问题 | 说明 |
| --- | --- | --- |
| D1 | 1.4 声明依赖「WMI、注册表、**PowerShell** 系统组件」，但 5.1–5.4 全部功能**没有一项真正需要 PowerShell** | 建议明确删除 PowerShell 依赖声明，改为「不调用任何脚本引擎（PowerShell/WSH）」。这是可验证的架构优势（见 A4） |
| D2 | 3.3.5「仅执行**本地**连通性探测…全程无用户数据上传」与实际探测 223.5.5.5 / 公网 TCP 443（**出站连接**）表述冲突 | 改为「仅执行面向公网可用性目标的**无载荷连通性探测**，不发送任何业务数据、不携带任何终端标识信息」 |

## 5. 缺失章节（E 类：PRD 应补，否则阶段 1/2/4 无依据）

| 编号 | 缺失内容 | 后果 | 建议补充 |
| --- | --- | --- | --- |
| E1 | **无验收标准（Acceptance Criteria）** | 阶段 4 测试无「通过」判据，阶段 7 无法判定可发布 | 每个 MVP 功能补 3–5 条可判定验收项（构造故障场景 → 期望告警文案） |
| E2 | **无非功能需求** | 轻量性只有定性描述，无法验证 | 建议：单次诊断总耗时 ≤ 30s；启动到首行输出 ≤ 3s；峰值内存 ≤ 50MB；EXE 体积 ≤ 15MB |
| E3 | **无边界/异常场景清单** | 大量真实终端场景未定义行为 | 补：无网卡、网卡被禁用、仅 IPv6、多网卡、VPN 隧道、WMI 不可用、非管理员、磁盘满、共享目录只读、虚拟机 |

| E5 | **无兼容性矩阵** | 无法声明支持范围 | 建议：Windows 10 1809+ / Windows 11 / Server 2019+，x64 优先（ARM64 可选） |
| E6 | **无失败处理策略总纲** | 单项失败行为不一致 | 定义统一约定：任何采集项失败**不得**导致程序崩溃或提前退出，必须降级并记录原因 |

## 7. 亮点确认（评审中应予保留和强化的部分）

1. **定位清晰且真实**：「只诊不修、只读安全」把合规约束转化为产品卖点，而非事后补丁 —— 这是 To B 工具的正确姿势，面试中极有说服力。
2. **差异化论证成立**：第 8 节对「原生工具 / 脚本 / RMM 平台」的三方对比抓住了本质 —— 价值不在「执行命令」，而在「结构化解析 + 自动判定 + 标准化报告」。
3. **报告三层结构设计专业**：告警汇总 → 结构化详情 → 原始数据附录，正好对应「快速定位 / 常规排障 / 深度溯源」三类使用者，是真实运维 Lead 会认可的设计。
4. **迭代路线克制**：V1.1 只读增强 → V1.2 台账与 dry-run → V2.0 才引入可控写操作，符合「先只读、后可控」的合规演进逻辑。
5. **5.5 负面清单**（明确不做自动修改 IP/DNS/注册表、不上传数据、不驻留、不弹窗）是 PRD 中最有工程素养的一段，建议在 README 与面试讲解中原样保留。
